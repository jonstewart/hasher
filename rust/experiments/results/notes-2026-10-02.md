# Development notes, 2026-10-02 (Xeon E5645, Westmere)

Hand-run sweeps on intermediate revisions while the lookup was being designed.
The numbers are from `hset bench` with 1 M queries at 50 % hits unless noted;
noise on this VM is about ±10 %, which matters for several of the comparisons
below. The committed report `xeon-e5645-westmere-2026-10-02.md` supersedes
these for anything about the final code.

## Baseline before the pipeline work (10 M SHA-1)

| strategy | single | batch |
|---|---:|---:|
| hull 18-bit, first version (k-ary single, lane batch) | 259 | 139 |
| legacy flat 8-bit | 566 | 216 |
| binary search | 1288 | 604 |

Window stats for the 18-bit hull table: mean 6.8 candidates, max 17, 3 MiB.
With the mean window at two or three cache lines, the remaining cost was
memory latency: table access, then window, then TLB walks on 4 K pages.

## Whole-window prefetch and staged batch (10 M)

Prefetching every line of a small window at once, and a three-stage software
pipeline for batches (table entry, window lines, search) replaced the lane
pipeline for small-window models:

| change | single | batch |
|---|---:|---:|
| before | 259 | 139 |
| after (staged, distance 12) | 217 | 97 |
| after, file copied to huge-page memory (`--copy`) | 191 | 100 |
| lanes forced instead of staged | 223 | 141 |

Huge pages helped single lookups (TLB walks) but not batches.

## Adversarial and small sets (first pipeline revision)

| set | hull (auto bits) | legacy flat 8-bit | binary search |
|---|---:|---:|---:|
| 2 M adversarial, 16 bits | 171 / 134 | 710 / 271 | 615 / 434 |
| 1 M uniform, 15 bits | 149 / 79 | 311 / 162 | 642 / 432 |

The legacy flat bound is slower than plain binary search on adversarial data
(its windows blow up); the hull line adapts its slope to the local density.

## Recursive dictionary search, first attempt

The first implementation prefetched the entire level-1 region even when the
sampled radius was thousands of hashes (no table: 1026 hashes, i.e. about
1600 lines per lookup), which is why it measured 6.1 µs per lookup. Capping
the region and re-aiming from the fetched edge key with the model's density
fixed it. After the fix (10 M):

| table | kary single / batch | recursive single / batch |
|---|---:|---:|
| none | 1169 / 602 | 489 / 598 (lane batch, bisection) |
| hull 0-bit | 836 / 327 | 627 / 324 |
| hull 8-bit | 459 / 210 | 441 / 207 |
| hull 12-bit | 304 / 156 | 287 / 163 |
| hull 14-bit | 273 / 178 | 282 / 175 |
| hull 16-bit | 203 / 96 | 201 / 97 |

Adding interpolating probes to the lane batch brought the hint-less batch
from 640 to 211 ns and the 0-bit table from 318 to 243 ns.

## Region cap and whole-window threshold at 40 M, 14-bit table (single ns)

| region-bytes | recursive |
|---|---:|
| 512 | 366 |
| 768 | 377 |
| 1024 | 403 |
| 1536 | 409 |

| window-bytes | kary | recursive |
|---|---:|---:|
| 1024 | 386 | 366 |
| 2048 | 378 | 393 |
| 3072 | 450 | 448 |

Larger regions and larger whole-window prefetches both got slower on this
core, consistent with its limited number of outstanding misses. Both
thresholds were therefore made runtime tunables for other hardware.

## Struct-of-arrays passes vs staged (batch ns)

A first, unpipelined passes version with 256-query sub-batches: 134 (10 M)
and 93 (1 M) against staged 98 and 74. Marginal perf counters (4 M minus
1 M queries, per lookup): staged 508 cycles, 354 instructions, 10.0 L1
misses; passes 597 cycles, 323 instructions, 16.9 L1 misses. Pipelining the
passes three sub-batches deep and vectorising the window arithmetic (LLVM
emits `pmuludq`) did not change the ranking:

| sub-batch | 10 M | 1 M |
|---|---:|---:|
| staged | 103 | 81 |
| 8 | 153 | 121 |
| 16 | 147 | 117 |
| 32 | 149 | 119 |
| 64 | 145 | 113 |

Marginal counters for passes with sub-batch 16: 410 instructions, 72 L1 loads,
13.6 L1 misses per lookup, against 370, 62, 10.2 for staged. The batch is
bound by memory stalls (IPC below one), so SIMD on the linear function has no
leverage on this core; the passes structure moves more data through L1.

## Bugs found by the oracle tests during this work

- Operator precedence in the 8-ary probe positions (`lo + (len*j) >> 3`),
  which made a window fail to shrink and a test loop forever.
- Ring-buffer aliasing in the staged pipeline, twice: the window ring needed
  2D slots, the key ring 3D, because a slot written for query i is read for
  i − D and i − 2D in the same iteration.
- Recursive search with equal primary keys at a region edge: a run of equal
  keys can extend below the fetched region, so equality at the lower edge has
  to search left rather than declare the lower bound inside the region.
- Fuzzing the decoder found two integer overflows on corrupted record lengths.
