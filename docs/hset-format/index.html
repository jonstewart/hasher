The hset file

A sorted array, its hints, the records behind it, and the TLSH vectors and index that ride along, byte by byte.

An hset is a file of hashes made for one question asked millions of times: is this digest in the set? Its answer to that question is a sorted array of fixed-width rows, memory-mapped and searched in place, with small precomputed hints that let a lookup touch only a handful of cache lines. Around that array the file carries optional records (the other fields hashed alongside each row), and for TLSH similarity digests two more structures: a matrix of embedding vectors and an inverted-file index for exact nearest-neighbour search.

This page is about the bytes. Three companion pages explain the algorithms the bytes serve.

1One file, seen whole

Figure 1 draws a real file to scale: test/md5_sha1_a-b.hset, 46,420 bytes holding 340 records, each with an MD5 and a SHA-1. Everything after the first 40 bytes is a sequence of chunks, and the first chunk is a table of contents that locates all the others. Two things dominate the picture: the record table (one 38-byte record per file hashed) and, per hash type, a section of four chunks: a header, a 4 KiB hint, the sorted rows, and an index back into the records.The hash sections start on 4096-byte boundaries, so every section is preceded by zero padding (dotted). The padding is what makes the hints look large here: the 4 098-byte HINT and the 3.6 KiB of padding after it together fill the gap to the next page.

2Chunks and the preamble

Every chunk has the same twelve-byte frame: a four-byte type that reads as ASCII, then a little-endian 64-bit payload length, then the payload. Nothing else in the file is self-describing; the frame is what lets a reader skip what it does not understand, and what lets hschunks.py hash each payload separately.All integers in the file are little-endian with two deliberate exceptions: chunk types, and the 16-bit hint type at the start of a HINT payload, are big-endian so that they read as text in a hex dump (FTOC, HH\x00\x01, b\x08).

Before the first chunk come 40 bytes: the magic string SetOHash and a SHA-256. The digest covers every byte from offset 40 to the end of the file, so it authenticates the table of contents, the headers, the rows and the hints together; the merge and build code compute it last, after every other byte is in place. Figure 3 is the real head of test/good.hset, a hash-sets-only file with one SHA-1 section.

3The table of contents

The FTOC payload is a flat array of twelve-byte entries, one per chunk in file order, FTOC itself included and FEND last. Each entry is the chunk's absolute byte offset (u64, little-endian) followed by its type (u32, big-endian, the same bytes as the chunk's own type field). A reader decodes the FTOC, then visits every listed offset in turn and checks that the type it finds there matches; the sequence of types must satisfy the grammar of §5.

The FTOC is written first but its contents are only known once the layout is final, so the builder sizes it from the number of fields when the output is opened and reserves room for every chunk a field might produce (a TLSH field may add TVEC and TIVF). The chunk is then written shorter than the reservation, and the gap before FHDR is zero.

4The file header

FHDR holds the format version and three strings. Strings throughout the file are pstrings: a 16-bit little-endian length followed by that many bytes, without a terminator.

5The chunk grammar

The decoder is a small state machine driven by the FTOC. After FHDR comes an optional record table (RHDR then RDAT), then any number of hash sections, then FEND. A hash section is a run of chunks that all belong to the HH header that opens it: a HINT (every hash type except sizes), the HDAT rows, and then only when the file has records a RIDX, and only for TLSH an optional TVEC and an optional TIVF, always in that order. A TVEC or TIVF after a non-TLSH section is a hard error.

6A hash section

A section opens with an HHnn chunk. The type field spells H, H and then a big-endian 16-bit number: the position of the hash algorithm's bit in the SFHASH_HashAlgorithm enum (MD5 is bit 0, SHA-1 bit 1, TLSH bit 15), so a reader recovers the algorithm as 1 << nn. The payload names the field, gives the row width and the row count.

HINT: the lookup hint

Next comes HINT, a payload that starts with a big-endian 16-bit hint type and continues with data that type defines. Two hint types exist. Every cryptographic hash section carries type 0x6208, the 8-bit block bounds: for each of the 256 possible leading bytes, the smallest and largest signed deviation of any stored row from its predicted position. The exact-lookup page explains what that prediction is and why the bounds make lookups fast; here it is enough that the payload is 2 + 256 × 16 = 4 098 bytes, always, whatever the set size.

TLSH sections carry hint type 0x7400 instead, the cell index of §8. The sizes field (8-byte file sizes, not uniformly distributed) carries no HINT at all and is searched by plain binary search.

HDAT: the rows

HDAT is the heart of the file: hash count rows of hash length bytes each, sorted in ascending bytewise order, nothing between them. The chunk is placed so that its 12-byte header sits on a 4096-byte boundary. Rows are unique in a hash-sets-only file; in a file with records two different records may carry the same digest, and then the digest appears twice, each copy pointing at its own record through RIDX.

RIDX: rows to records

When the file has a record table, each HDAT is followed by RIDX: one little-endian u64 per row, the index of the record the row came from. The rows of a section are sorted by their own value, the records by their full bytes; the two orders agree only for the first record field, so RIDX is in general a permutation. sfhash_hashset_record_for_hash is a single array read: rdat + RIDX[row] × record_length.

7Records

A record is everything that was hashed about one input: its MD5, its SHA-1, its size, its TLSH, whichever fields the set was built with. RHDR declares the fields; RDAT is the fixed-width record table. Field order is the order given when the builder was opened, and it fixes the record layout: each field is a presence byte (0 or 1) followed by the field's value, zero-filled when absent. A TLSH column of TNULL, or any empty column, is written absent and contributes no row to its hash section.

Records are sorted by their full bytes and deduplicated before writing, so identical inputs collapse to one record, and the record count in RHDR is the number of distinct records. Because the presence byte comes first within each field, all records lacking their first field sort before all records that have it.

8TLSH hash sections

A TLSH section stores rows of 36 bytes: the canonical digest below rather than the 70-character hex form. The byte order was chosen so that the ordinary bytewise sort used for every other hash type yields the canonical TLSH order L, Q1, Q2, body, checksum. The two body planes keep the high bits and the low bits of the 128 two-bit bucket codes apart, which is what makes the distance kernel on the TLSH page three popcounts instead of 32 table lookups. The all-zero row is TNULL and never appears.

HINT 0x7400: the cell index

The first two bytes of a row, L and Q, define its cell: c = L ≪ 8 | Q, one of 65 536. Because rows are sorted and these are the leading bytes, every cell is a contiguous run of HDAT. The hint stores where each run starts.

TVEC: the vectors

Optionally, after HDAT and RIDX, a TLSH section carries TVEC: the 264-dimensional float32 embedding of every row, in row order. The payload has a 32-byte header; the chunk is positioned so the matrix itself begins on a page boundary, which lets numpy, faiss or scikit-learn map it straight from the file.

TIVF: the inverted-file index

Last in a TLSH section comes TIVF, the index that makes exact nearest-neighbour search fast. Structurally it is a two-level CSR: cells point at ranges of lists, lists point at ranges of row ids. Each list carries a medoid (a 36-byte digest, the list's centre) and radius2, the largest squared body-embedding distance from the medoid to any member. Those two values are the whole of what the search relies on: how the rows were partitioned into lists is the writer's business, and the TLSH page describes libhasher's two builders.

9Alignment and integrity

Two alignment rules shape the file. Every HDAT chunk starts on a 4096-byte boundary, so the rows of each section begin 12 bytes into a page and a section's pages are its own. Every TVEC chunk is placed so that its data starts on a boundary: offset(TVEC) + 12 + 32 is a multiple of 4096. Zero bytes fill the gaps, and the FTOC never lists them.

Integrity rests on the SHA-256 at offset 8, computed over [40, end). A reader additionally checks: the magic; that every FTOC entry's offset holds a chunk of the listed type; that the chunk sequence obeys the grammar; that each HDAT is exactly count × length bytes, each RIDX count × 8, RDAT record_count × record_length; the hint type, the 0x7400 offsets (first 0, last n, non-decreasing); the TVEC header and its size; and the TIVF header, its total length and its two offset arrays. It does not read the TIVF ids or verify the sort order at load time; both would touch every page of the file.
