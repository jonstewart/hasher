Set operations

Union, intersection and difference of whole files by one merge pass, with the hints, the records and the TIVF index carried through a row map instead of rebuilt.

A master hash set absorbs new rows every hour, an analyst wants the intersection of two collections, a corpus minus its known-good subset. Each of these is a set operation on whole files, and each output must be a complete, valid hset: sorted rows, hints, records, and for TLSH the index. The naive route rebuilds everything from the union of the inputs: a sort and a clustering. hset instead merges: a single two-pointer pass over the two sorted inputs decides every row's fate, and every other chunk is carried through that decision by a row map. Nothing is re-sorted or re-clustered. The hard part is the TIVF index, whose lists must stay correct and must not multiply.An hourly union of 18 000 rows into a 1M-row master takes about 42 ms with the index carried through, against 440 ms for a rebuild with the integer builder and 3.3 s with the float one; the daily 432 000-row batch takes 100–150 ms against 2.5 s. 1Two pointers

Both inputs are sorted, so the classic merge applies: one cursor per input, compare the rows at the cursors, emit the smaller (or, when equal, the left one) and advance. The operation decides what is emitted: union emits everything, intersection only values present on both sides, difference only left values with no equal on the right. Equal runs within one input are skipped as a unit, so a hash-sets-only output never contains a duplicate. The pass costs one comparison per input row and produces, as a side effect, the two maps that drive everything else: for each input row, its output position, or "dropped".

2Everything else follows the map

The output file has the same chunks as a built file, and each one is produced from the inputs through the maps without any global computation over the rows.

  • HDAT: every kept input row is copied to its mapped position. The output is sorted because the merge emitted in order.
  • HINT: the hints depend only on the written rows, so they are recomputed from the output HDAT: the per-block deviation bounds in one pass, the TLSH cell index as a count per cell and a prefix sum.
  • RIDX: each kept row's record index is pushed through the record map of §3.
  • TIVF: the subject of §4 and §5. When one input has no index and the output wants one, the merged rows are clustered from scratch instead.

Whether the output gets the optional TLSH index is a choice: explicitly, or by inheritance, which writes it if and only if every input that has a TLSH section has one. Under inheritance an index is always merged, never rebuilt.

3Records

When both inputs carry a record table, the operation is applied to the records, and the rows follow. Records are first widened to a common layout: the left input's fields in their order, then any fields only the right has; an absent field is a zero presence byte and a zero value. A side whose field order changed by the widening is re-sorted. The widened records are then merged by the same two-pointer rule, comparing whole records, and identical records collapse to the left copy. For intersection and difference only left records can be emitted, so the right record map is all "dropped".

Then the hash sections are merged under the records' decisions: a row is emitted if and only if its record was. Two equal rows that belong to two different kept records stay two rows (that is how the builder writes them, and each still points at its own record), while a hash-sets-only output of a record-level operation writes each distinct row once. When only one input has records, or neither, the output is a hash-sets-only file and the rows are merged as sets. A records-only input can only be merged with another records-only input.

4Merging the TIVF lists

The index is where rebuilding would be expensive and where merging has to be careful. The TIVF contract is per list: every member lies within radius2 of the medoid. The row maps let the lists be carried across the merge cell by cell, because a row's cell (its first two bytes) is the same in the output as in the input, and because both maps are increasing over the kept rows, so a list's ids stay ascending after remapping.

For each cell the merge gathers the left input's lists, then the right's, and remaps every id. Dropped ids are removed; a list that loses all its members disappears. A list that loses some members has its radius recomputed exactly over the survivors, about its old medoid, which stays its medoid whether or not it is still a member. A list that lost nothing keeps its medoid and radius untouched, since a radius depends only on the list's members. Exactness is preserved at every step: the search never relies on the medoid being a member, only on the radius bound.

5Coalescing

Concatenation alone has a flaw: lists accumulate. A batch of 18 000 rows spreads over thousands of cells, adding a tiny list to each; after a day of hourly merges a cell holds dozens of fragments where a fresh build would have one list, and a query pays a bound evaluation for each. The merge therefore coalesces small lists. With threshold C (64 by default, twice the fresh build's target list size), while a cell has two lists of fewer than C/2 rows each, the pair whose union has the smallest exact radius about one of the two medoids becomes one list: that medoid, that radius, the sorted union of the ids. A pair always sums to fewer than C rows, and the loop ends with at most one list under C/2 per cell.

What the invariant does not bound is rows scanned: a coalesced list has the radius of a pair that a fresh clustering might have kept apart, so its bound is looser and more of its rows may be visited. That is measured rather than proven, and the sweep below is the measurement.

6What it costs, what it keeps

A merged index is never incorrect; it can only be slower than a fresh one, and the sweep bounds how much: after 24 hourly merges the index answers in 29.6 µs against 28.9 µs rebuilt, scanning 16 900 rows against 12 400. The hard case is a batch that is a large fraction of the master: after seven daily batches of 432 000 rows the merged index scans 1.8× the rows of a rebuild and answers in 1.3× the time, still two orders of magnitude under brute force.
