TLSH, embedding and index

From a 36-byte similarity digest to a Euclidean lower bound, and from the bound to an exact nearest-neighbour index that reads a few thousand rows per query.

TLSH is a similarity digest: two files that differ a little get digests that differ a little, and the TLSH distance between digests, a weighted sum of 128 bucket differences and a few header terms, scores how alike the files are. The question an hset must answer for TLSH is not "is this digest in the set" but "which rows are near this digest", and a sorted array does not help with that. This page builds, in order: the digest and its distance; a lower-bound embedding into Euclidean space; the cell index that makes the header part of the distance exact; the TIVF index that bounds the body part per list of rows; and the search that puts them together to answer k-nearest-neighbour queries exactly, touching a few thousand rows instead of millions.Everything numeric on this page is computed by the generator from the real 49 997-row TLSH set in test/inc_master.hset (its HDAT and TIVF payloads are copied into the build directory) with a Python re-implementation of the library's kernel and search, which it checks against brute force on every query it runs.

1The digest

A TLSH digest has a three-byte header and a 32-byte body. The header is L, a logarithmic measure of the input length; Q1 and Q2, two quartile ratios packed in one byte; and a one-byte checksum. The body is 128 buckets, each holding a two-bit code (0–3) that says in which quartile that bucket's count fell. The familiar 70-character hex string is a transport encoding that swaps the nibbles of the header bytes and writes the body backwards; libhasher unpacks it once into the 36-byte canonical row of Figure 1, which is what the file stores.

2The distance

The reference TLSH distance is a sum of independent terms. L contributes 0, 1 or 12k for a circular difference of k; Q1 and Q2 each contribute 0, 1 or 12(k − 1); the checksum contributes 1 when it differs; and each of the 128 buckets contributes 0, 1, 2 or 6 for a code difference of 0, 1, 2 or 3. Scores up to about 30 mean near-identical inputs, and above 100 or so the digests carry no similarity information at all.

3Three popcounts

Summing 128 table lookups per pair is what the reference implementation does, at about 9.5 ns per row. The bit planes turn the body cost into bit arithmetic. With X the XOR of the low planes, Y the XOR of the high planes and S the mask of buckets where the first digest's two bits agree (codes 0 or 3), the per-bucket cost is exactly

popcount(X ⊕ Y) + popcount(Y) + 5 · popcount(X ∧ Y ∧ S)

as the sixteen cases of Figure 4 verify. The first term counts buckets whose codes differ by an odd amount, the second those whose high bit differs, and the third picks out the one expensive case, a 0 against a 3, which the first two terms have already charged 1 for.

Per query the kernel holds the query's planes and S in registers, so a row costs two 16-byte loads, three vector XOR/AND operations, three byte-wise popcounts and one horizontal sum. On arm64 NEON that is 0.55 ns per row, seventeen times the reference; on x86 the same expression runs on two 64-bit halves with the POPCNT instruction.

4The embedding

Pruning needs geometry: a way to say "no row in this group can be close" without visiting the rows. TLSH distance is not a Euclidean metric, but it can be bounded below by one. The embedding φ maps a digest to 264 float coordinates such that the squared Euclidean distance between two embeddings never exceeds their TLSH distance. Each cost term gets its own orthogonal block of coordinates, so the bound is the sum of per-term bounds, and each term is bounded by the tightest placement that the term's cost function allows.

5Cells: the header made exact

The first two bytes of the canonical row, L and Q, are also the leading bytes of the sort key, so all rows with the same (L, Q1, Q2) are one contiguous run: a cell, one of 65 536, located by the 0x7400 hint. This has a consequence the embedding alone could not give. Within a cell the header part of the distance to a query is a constant, computed exactly once from three circular differences; only the checksum term (0 or 1) and the body vary from row to row. The header does not need to be embedded, bounded or approximated at all. It also removes the 144 cap: the L coordinate was the only reason for it.The first design grouped lists by L alone, with 264-dimensional float centroids. It was slower than the plain cell index (777 µs against 16 µs per query at 1M rows) and valid only up to distance 144. Grouping by cell made the header exact, cut the query to 44 µs, and the medoid-plus-integer-radius representation of the next section cut it to 26 µs; the NEON kernel and list size 32 brought it to 8 µs.

6The TIVF index

Inside a cell the body still has to be searched. TIVF partitions each cell's rows into lists of about 32 rows that are close in body-embedding space, and summarises every list by two numbers the search can use without touching the rows: a medoid, a digest central to the list, and radius2, the largest squared body-embedding distance from that medoid to any member. The on-disk structure is the two-level CSR of the format page: cells → lists → row ids. The contract between writer and reader is only this: every member of a list lies within radius2 of its medoid. Any partition that keeps it gives an exact search; a good partition gives a fast one.

7Building the lists

The default builder, BISECT, uses integer arithmetic only, so the index bytes are identical on every platform for the same rows. A cell of more than 4 096 rows is first split coarsely: two far-apart members are chosen as pivots and every row goes to the nearer one, recursively, until every node is at most 4 096 rows. Each node is then clustered flat by k-means into ⌈s/32⌉ lists over centroids that are exact integer sums.

Finally each list gets its medoid: the exact 1-center, the member whose maximum distance to the other members is smallest. That minimises radius2 among members and so minimises how far the list's bound can be from the truth.

The alternative builder, KMEANS, runs ordinary float k-means++ over a whole cell and takes as medoid the member nearest each centroid; it produces lists of the same quality at ten to twenty times the build time, and its bytes depend on the compiler's float arithmetic. Build time is dominated by the largest cells: at 1M synthetic rows BISECT builds the index in 136 ms against 1.5 s, at 4M in 1.3 s against 26 s.Rejected along the way, by rows scanned per query at 1M: pure recursive bisection down to list size (13 533 rows, a hard two-way split cuts families across the boundary), flat k-medoids (11 627; a single row is a poor centre in 256 dimensions), and coalescing small lists in a fresh build (it pairs unrelated families into wide lists). BISECT with flat integer k-means scans 4 659 rows, k-means 4 848.

8The search

Given a query q, k and a maximum distance, the search keeps a bounded max-heap of the k best (distance, row) pairs found so far, ordered so that the worst of them is on top; τ, the largest distance still worth finding, starts at max_distance and drops to the top's distance once the heap is full. Three nested prunings cut the work.

  1. Cells in header-cost order. L values are visited as L, L±1, L±2, …, and for each, Q bytes in the order of a static table sorted by q_cost(k1) + q_cost(k2), translated to the query. Both loops stop as soon as their cost alone exceeds τ. No sorting happens per query.
  2. Lists by their bound. In a visited cell with several lists, one kernel call per medoid gives each list's floor b; lists with ch + b ≤ τ are scanned in increasing b, and the scan stops at the first that no longer passes, since τ only shrinks. A cell with a single list is scanned contiguously (its ids are the cell's own row range), and a list of fewer than four rows is scanned without evaluating its bound.
  3. Rows. A scanned row costs a checksum compare and one kernel evaluation; rows with distance ≤ τ go into the heap.

9A real query, traced

The generator takes a row of the real set, mutates a few bucket codes and runs the search for k = 10 within distance 144, against the index and by brute force. The query digest is T1BCD2AF6AD7BE372B1C86CD…; its nearest rows are row 40822 at distance 11, row 40821 at distance 12, row 40823 at distance 16. The index visited 156 cells, evaluated 143 list bounds and computed 2,386 row distances, out of 49,997, and returned the same ten rows as brute force.

On the 1M-row corpus the index answers a query in about 8 µs on an Apple M-series core against 566 µs for the kernel brute force and 9.5 ms for the reference implementation; on the VM's Xeon with 200 queries per set, 0.65 ms for member queries and 3.8 ms for uniformly random digests against 8.2 and 8.6 ms brute force. Random digests are far from everything, so τ stays large and pruning is weak; that is the regime where the bound's looseness shows.
