Exact lookup

How a sorted array of random digests becomes a line, how the file records the line's error, and how a lookup touches a handful of rows.

Exact lookup is the question the file was built for: given a digest, is one of the n sorted rows equal to it? Binary search answers in ⌈log₂ n⌉ probes, and on a 40-million-row set that is 26 probes, each of them a cache miss into an 800 MB array that no cache holds. The hint stored in every hash section cuts the probes to about nine, and a batch interface overlaps the misses of independent lookups. This page shows why the hint can be so small (4 KiB for any set size) and how far the idea was pushed before the simplest version won.

1A sorted array of random numbers is a line

A cryptographic digest is, for every purpose here, a uniformly random bit string. Sort n of them and plot each row's value against its index: the points lie almost exactly on the diagonal, because a uniform value h lands at the fraction h/2bits of the way through the set. The sorted array is the quantile function of a uniform distribution, and that function is a straight line.Correctness never depends on this. The bounds in §4 are computed over every stored row, so a query equal to a stored row is always inside its window. Uniformity decides only how narrow the window is, which is to say how fast the lookup is; the eval included a deliberately skewed, clustered "adversarial" set, and every strategy stayed exact on it.

2The predicted index

The line gives every hash a predicted or expected index e(h) = ⌊h · n / 2bits⌋. Only the leading bits of h can matter when n fits in 32 bits, so the code takes the first four bytes as a big-endian 32-bit integer h₃₂ and computes (h₃₂ · n) ≫ 32 in a single 64-bit multiply that cannot overflow: no memory is touched, and no floating point is involved.

3The error is a random walk

Subtract the prediction from the truth and plot d = i − e against e. Figure 3 shows the result for the same 4 096 digests, drawn as a connected line in order of e. It is not noise: it is a random walk pinned to zero at both ends, a Brownian bridge, because d(e) counts how many rows fell below their predicted position so far, and each new row changes that count by at most one. Its excursion is about ±√n/2 overall, but between neighbouring e values it barely moves.For n = 40 million the whole bridge wanders about ±3 000 rows, yet within one 8-bit block of 156 000 consecutive rows it varies by only a few hundred, and within a 14-bit block of 2 400 rows by a few tens. That locality is why a per-block band is tight and why finer blocks are tighter still.

That is the whole opportunity. A query's row, if it exists, sits at e + d for some d the walk took near e. If the file records how far the walk strayed in the neighbourhood of e, the search can be confined to that strip.

4The hint: observed error per block

The 0x6208 HINT is exactly Figure 3's blue steps. The writer passes once over the sorted rows; for each row it computes d and folds it into the running minimum and maximum of the row's block, the block being the row's leading byte. Because e grows with h, the 256 blocks are also 256 equal slices of the e axis, each n/256 rows wide. The result is 256 pairs of signed 64-bit integers, 4 098 bytes with the type tag, regardless of n. A block no stored hash begins with keeps the sentinels (INT64_MAX, INT64_MIN), which the reader recognises as "certain miss".The eval's winning variant used 14-bit blocks keyed by the first two bytes (16 384 blocks, 256 KB), 1.3–1.6× faster than 8-bit blocks on 40M rows. It is not what the file stores today: a fixed 256 KB table is larger than the data for a 10 000-row set, and the size-adaptive scheme the analysis recommends was left as an open decision. The header of a HINT carries the type precisely so a later block size can be added.

5The window and the search inside it

At query time, the window is two additions: lo = e + minb, hi = e + maxb + 1, clamped to [0, n). The stored row, if present, has the same leading byte and the same e as the query, so its d lies within the block's recorded range and the row lies within the window.

Inside the window the code runs a branchless lower-bound search on the primary key, the first eight bytes of each row read as one big-endian integer. Random keys make an ordinary binary search's branch unpredictable, so half its comparisons mispredict; the branchless form computes both outcomes and selects with a conditional move, and its loop runs a fixed ⌈log₂ len⌉ times. Only when a probe's primary key equals the query's are the remaining bytes compared, and two different 20-byte digests sharing eight leading bytes is a one-in-264 event.

6Many lookups at once

A single lookup is latency-bound: each probe's address depends on the previous probe's result, so its cache misses are serial. Scanning a disk image produces thousands of independent queries, and sfhash_hashset_lookup_bulk exploits that. It keeps D = 32 queries in flight as lanes; each round advances every active lane by one probe and immediately prefetches the cache line of that lane's next probe. The hardware then has up to 32 misses outstanding instead of one. Results are bit-identical to calling the single lookup on each query.

7Fitting lines to the error

A flat band per block is the crudest possible fit to the walk: slope zero, height max − min. The evaluation harness tried to do better by fitting lines. Within a block the walk often trends, and a sloped slab d ∈ [s·e + clo, s·e + chi] can be narrower than the flat band. The narrowest enclosing slab of a point set is found through its convex hull: the optimal slope is the slope of some hull edge, so the builder computes the upper and lower hulls, tries each edge's slope, and keeps the one whose slab is thinnest. The three numbers are stored as floats and then verified and widened: every stored row is re-checked with the stored floats and clo or chi is nudged out by one until none falls outside, which keeps float rounding from ever excluding a real row.

Taken to its limit, the idea gives one global pair of hulls over all n points: a piecewise-linear upper and lower bound on the walk, tight everywhere, with a few dozen vertices. A query locates its segment by binary search over the vertices and interpolates; the window is the tightest of any candidate. A third family, interpolation search, uses the keys at the window's ends to estimate where the query falls inside it.

8What the measurements said

All candidates were raced on the same frozen harness against a std::binary_search oracle, on synthetic sets, an adversarial set, and the real NSRL SHA-1 and MD5 sets of 40.4 million rows. The ranking was cross-checked against machine-independent probe counters and hardware cache-miss counters. The result overturned the plan: the flat band at a finer resolution beat every line fit.Why: on a memory-latency-bound problem the window computation must cost nothing, and a flat band costs one integer add. The sloped slab needs two float multiplies and a floor and ceil; the global hull a binary search over its vertices; interpolation two extra dependent reads of the window's end keys, which break the memory-level parallelism of the batch pipeline, so c6's batch mode came out three times slower than c1's.

The block-bound mechanism scales as the random-walk picture predicts. On a 262,144-row simulated set, the generator measured these windows:

9TLSH rows: the cell index

TLSH digests are not uniform: their first byte is a log-scaled file length, so most rows crowd into a few dozen L values. The expected-index trick would fail them, and their section carries the 0x7400 hint instead: 65 537 offsets that locate the run of rows sharing the digest's first two bytes. A lookup reads L and Q, takes the run [offset[c], offset[c+1]) with c = L ≪ 8 | Q, and binary-searches inside it. With rows spread over a few thousand non-empty cells the run is typically a few dozen rows, and the search touches five or six of them.
